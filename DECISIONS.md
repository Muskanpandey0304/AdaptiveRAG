# Design Decisions

One line per decision not already pinned down by the spec: the choice and the reason.

- **LLM provider: Ollama.** User chose it in setup so the project needs no API key and runs fully offline/local.
- **Python version: 3.10 (via venv), not the system default 3.14.** 3.14 is too new; `faiss-cpu` and `torch` (a `sentence-transformers` dependency) don't yet publish wheels for it.
- **LLM SDK for Ollama: the `ollama` PyPI package.** It's the official lightweight client and keeps `src/llm.py` a thin wrapper rather than hand-rolled HTTP calls.
- **`.gitignore` scoped to secrets and generated artifacts** (`.env`, `venv/`, `data/index/`, `logs/*.jsonl`, `eval/results.md`, `eval/to_grade.csv`) from Step 1 onward, not deferred to Step 10, so nothing generated or secret gets committed while building step by step.
- **`test_llm.py` skip condition: "no local Ollama server", not "no API key".** The spec's accept criterion was written for key-based providers; Ollama has no key, so the thing that actually blocks the test on a fresh machine is the server not running (checked via `ollama.list()`). Same intent (skip, don't fail, when the provider isn't usable here), adapted to the provider that was actually chosen.
- **Retry-once implementation: a plain `try` then one unconditional retry on any `Exception`,** not a narrower exception type. The `ollama` client doesn't expose a distinct "transient vs. permanent" error type, so narrowing would be guesswork; a single retry is cheap even for a non-transient error (fails the same way twice, no harm done).
- **Latency measured with `time.perf_counter()` around the call**, not Ollama's own `total_duration` field. Wall-clock time is what the rest of the pipeline (and the eval step) cares about, and it works uniformly if a future provider doesn't report its own timing.
- **`clean_text` preserves blank-line paragraph breaks (as `\n\n`) instead of collapsing all whitespace uniformly.** `chunk_pages` needs paragraph boundaries to split on; collapsing everything to single spaces first would erase them. In practice, PDF text extraction rarely encodes real blank-line paragraph breaks, so chunking mostly falls through to the sentence-boundary step anyway — accepted as the simplest faithful reading of "split on paragraph, then sentence boundaries."
- **`chunk_pages` caps every pre-chunk "unit" (paragraph/sentence) at `CHUNK_TOKENS`, splitting an oversized unit by fixed-size word groups as a last resort.** Without this, a single very long run-on sentence could produce a chunk over the `CHUNK_TOKENS * 1.5` acceptance limit; the spec only mandates paragraph/sentence splitting, so this is an added safety net, not a new design choice.
- **`tests/test_ingest.py` tests `chunk_pages`/`clean_text` directly with small synthetic page dicts, not real PDFs.** `data/raw/` is still empty (user hasn't supplied documents yet); per the spec's rule against inventing data, we don't fabricate fake PDFs to stand in for the real corpus. Running `python -m src.ingest` against the empty folder correctly prints a message and writes nothing, rather than fabricating `chunks.json`.
- **`tests/test_indexer.py` builds indexes from small synthetic chunks, not `data/index/chunks.json`.** Same reason as Step 3: that file doesn't exist yet since no real PDFs have been ingested. `python -m src.indexer` checks for it and refuses with a clear message instead of inventing chunks to index. First test run downloads `BAAI/bge-small-en-v1.5` (~130MB) from Hugging Face and caches it; later runs are fast.
- **`tests/test_retrievers.py` builds a small synthetic (FastAPI-flavored) corpus in a fixture, not the real index.** Same reason again: no real PDFs ingested yet. The test corpus exercises the retrieval *algorithms* (sortedness, k, dedup, RRF's rank-overlap property, reranking) rather than claiming any real retrieval quality.
- **RRF's rank-overlap property is unit-tested via a private `_fuse_rrf` helper with hand-picked rank lists**, not by trying to coax real embeddings/BM25 into a controlled overlap. `hybrid_search` calls the same helper, so this is testing the real fusion logic, just decoupled from retrieval-quality variance.
- **Step 5's full demo ("print top-3 of each method for 5 user-provided queries") is deferred.** It needs both a real indexed corpus and 5 real queries from the user — neither exists yet (`data/raw/` is empty). Flagged to the user rather than faked with placeholder queries against a synthetic corpus.
- **`test_generator.py` mocks `src.generator.generate` (the name imported into that module), not `src.llm.generate`.** Monkeypatching has to target the name as looked up at call time, which is the local binding in `generator.py` after `from src.llm import generate`.
- **Step 6's live baseline demo ("plain vector top-5 RAG on 3 user questions") is deferred, same as Step 5's.** It needs a real indexed corpus, a running local Ollama server, and 3 real questions from the user — none of which exist yet. The commit is still tagged `baseline-simple-rag` since the tag marks *this code* (the simple top-5-vector-then-generate path) as the baseline to compare the router against later, not a specific live run.
