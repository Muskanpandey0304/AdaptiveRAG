# Design Decisions

One line per decision not already pinned down by the spec: the choice and the reason.

- **LLM provider: Ollama.** User chose it in setup so the project needs no API key and runs fully offline/local.
- **Python version: 3.10 (via venv), not the system default 3.14.** 3.14 is too new; `faiss-cpu` and `torch` (a `sentence-transformers` dependency) don't yet publish wheels for it.
- **LLM SDK for Ollama: the `ollama` PyPI package.** It's the official lightweight client and keeps `src/llm.py` a thin wrapper rather than hand-rolled HTTP calls.
- **`.gitignore` scoped to secrets and generated artifacts** (`.env`, `venv/`, `data/index/`, `logs/*.jsonl`, `eval/results.md`, `eval/to_grade.csv`) from Step 1 onward, not deferred to Step 10, so nothing generated or secret gets committed while building step by step.
- **`test_llm.py` skip condition: "no local Ollama server", not "no API key".** The spec's accept criterion was written for key-based providers; Ollama has no key, so the thing that actually blocks the test on a fresh machine is the server not running (checked via `ollama.list()`). Same intent (skip, don't fail, when the provider isn't usable here), adapted to the provider that was actually chosen.
- **Retry-once implementation: a plain `try` then one unconditional retry on any `Exception`,** not a narrower exception type. The `ollama` client doesn't expose a distinct "transient vs. permanent" error type, so narrowing would be guesswork; a single retry is cheap even for a non-transient error (fails the same way twice, no harm done).
- **Latency measured with `time.perf_counter()` around the call**, not Ollama's own `total_duration` field. Wall-clock time is what the rest of the pipeline (and the eval step) cares about, and it works uniformly if a future provider doesn't report its own timing.
- **`clean_text` preserves blank-line paragraph breaks (as `\n\n`) instead of collapsing all whitespace uniformly.** `chunk_pages` needs paragraph boundaries to split on; collapsing everything to single spaces first would erase them. In practice, PDF text extraction rarely encodes real blank-line paragraph breaks, so chunking mostly falls through to the sentence-boundary step anyway — accepted as the simplest faithful reading of "split on paragraph, then sentence boundaries."
- **`chunk_pages` caps every pre-chunk "unit" (paragraph/sentence) at `CHUNK_TOKENS`, splitting an oversized unit by fixed-size word groups as a last resort.** Without this, a single very long run-on sentence could produce a chunk over the `CHUNK_TOKENS * 1.5` acceptance limit; the spec only mandates paragraph/sentence splitting, so this is an added safety net, not a new design choice.
- **`tests/test_ingest.py` tests `chunk_pages`/`clean_text` directly with small synthetic page dicts, not real PDFs.** `data/raw/` is still empty (user hasn't supplied documents yet); per the spec's rule against inventing data, we don't fabricate fake PDFs to stand in for the real corpus. Running `python -m src.ingest` against the empty folder correctly prints a message and writes nothing, rather than fabricating `chunks.json`.
- **`tests/test_indexer.py` builds indexes from small synthetic chunks, not `data/index/chunks.json`.** Same reason as Step 3: that file doesn't exist yet since no real PDFs have been ingested. `python -m src.indexer` checks for it and refuses with a clear message instead of inventing chunks to index. First test run downloads `BAAI/bge-small-en-v1.5` (~130MB) from Hugging Face and caches it; later runs are fast.
- **`tests/test_retrievers.py` builds a small synthetic (FastAPI-flavored) corpus in a fixture, not the real index.** Same reason again: no real PDFs ingested yet. The test corpus exercises the retrieval *algorithms* (sortedness, k, dedup, RRF's rank-overlap property, reranking) rather than claiming any real retrieval quality.
- **RRF's rank-overlap property is unit-tested via a private `_fuse_rrf` helper with hand-picked rank lists**, not by trying to coax real embeddings/BM25 into a controlled overlap. `hybrid_search` calls the same helper, so this is testing the real fusion logic, just decoupled from retrieval-quality variance.
- **Step 5's full demo ("print top-3 of each method for 5 user-provided queries") is deferred.** It needs both a real indexed corpus and 5 real queries from the user — neither exists yet (`data/raw/` is empty). Flagged to the user rather than faked with placeholder queries against a synthetic corpus.
- **`test_generator.py` mocks `src.generator.generate` (the name imported into that module), not `src.llm.generate`.** Monkeypatching has to target the name as looked up at call time, which is the local binding in `generator.py` after `from src.llm import generate`.
- **Step 6's live baseline demo ("plain vector top-5 RAG on 3 user questions") is deferred, same as Step 5's.** It needs a real indexed corpus, a running local Ollama server, and 3 real questions from the user — none of which exist yet. The commit is still tagged `baseline-simple-rag` since the tag marks *this code* (the simple top-5-vector-then-generate path) as the baseline to compare the router against later, not a specific live run.
- **`force_route="vector"` runs plain top-`TOP_K` vector search then generate** — not a route the router itself ever produces, only reachable via `force_route`. It's the same shape as the Step 6 baseline (tagged `baseline-simple-rag`), kept in `pipeline.py` so Step 8's eval can run it in isolation alongside `direct`/`keyword`/`hybrid` without duplicating logic.
- **The "confidence" field means different things per route** (BM25 score for keyword, vector cosine or rerank score for hybrid/vector, `None` for direct) rather than one normalized number. The spec only defines what triggers each route's own threshold check; reusing that same checked value as `Result.confidence` keeps logging honest about what was actually compared, rather than inventing a fake common scale.
- **`_run_hybrid`/`_run_vector` are shared by the router-chosen path and keyword-route escalation** (escalation literally re-runs the hybrid flow per the spec), so there's one place that applies the `VECTOR_MIN_SIM` gate and the `NOT_FOUND` rewrite, not two copies that could drift.
- **The router test's 28 labeled queries were reviewed and approved by the user before committing**, per the spec's explicit "written by the agent, reviewed by the user" instruction for this step.
- **The one mandated pipeline test (out-of-domain → "Not found") uses a synthetic FastAPI-flavored corpus**, same reasoning as Steps 3-5: `data/raw/` has no real PDFs yet. It injects the synthetic `Retriever` by monkeypatching `pipeline._retriever` directly (bypassing the lazy-build check in `_get_retriever`), keeping `ask()`'s public signature exactly as specified (no test-only parameter added). The low-confidence gate meant this ran fully offline — no live LLM call was needed to prove the "Not found" behavior.
- **Step 8 (`src/eval.py`) was implemented and unit-tested, but not run end-to-end**, since both `eval/questions.json` and real PDFs in `data/raw/` are still missing — the user explicitly chose "write the code now, run it later" when asked, rather than supplying the files immediately. `load_questions()` refuses loudly (`SystemExit`) instead of inventing questions, matching the spec's explicit stop-and-ask instruction for this step. Only the pure data-processing functions (`hit_at_5`, `summarize_config`, `render_results_md`, `write_to_grade_csv`, `_mean`/`_p95`) are unit-tested with synthetic `Result`/record fixtures; `run_config`, `tune_thresholds`, and `main()` all call the live pipeline and are untested until real data exists.
- **`tune_thresholds` computes each question's confidence once per retrieval mode (keyword/hybrid) and reuses it across all swept threshold candidates**, rather than re-running `ask()` per threshold. Confidence doesn't change with the threshold — only the gate decision does — so this is strictly cheaper and still faithful to what the sweep is measuring.
- **The sweep's "hit rate" is reframed as "answer rate"** (fraction of questions where confidence clears the candidate threshold) rather than literal `hit@5` (whether the gold chunk was retrieved) — `hit@5` doesn't depend on the confidence threshold at all (the threshold only gates whether an answer is attempted, not what gets retrieved), so reusing that term for the sweep would have been misleading.
- **`CONFIGS["bm25"]` maps to `force_route="keyword"`** (not a route name of its own) since `pipeline.py`'s keyword route *is* a BM25 search; eval just needs it run without escalation, which `force_route` already guarantees.
- **`app.py`'s acceptance criteria were verified two ways**: a literal `streamlit run app.py --server.headless true` (confirmed HTTP 200, then stopped), and Streamlit's `AppTest` headless harness (`tests/test_app.py`) for interaction behavior -- no real browser is available in this environment, and `AppTest` is Streamlit's own first-party tool for exactly this. The out-of-scope "Not found" check reuses the synthetic-corpus injection pattern from `tests/test_pipeline.py`, since `data/raw/` still has no real PDFs.
- **README's "Related work" names were verified by fetching their actual pages**, not written from the spec's bare names. A first web search turned up nothing for `adaptive-rag-engine`, ArgusLens, or Augur; the user supplied the real URLs (PyPI + two GitHub repos), which were then fetched directly and described using only what those pages state, per the user's explicit instruction not to add unverifiable detail.
- **The README's Evaluation and "what worked / what didn't" sections are left as explicit "pending" placeholders**, not filled with plausible-looking numbers, since `eval/results.md` doesn't exist yet (no real PDFs, no real `eval/questions.json`). This is the same rule applied consistently through every step: evaluation numbers are never invented, only reported once a real run exists.
- **Architecture diagram uses Mermaid** (GitHub/most Markdown viewers render it natively) over ASCII, since the pipeline's branching (escalation, rerank toggle, confidence gate) is easier to follow as a flowchart than fixed-width box art; the spec allows either.
- **Neighbor expansion added post-spec, at the user's request**, to address chunk-boundary fragmentation (an answer split across adjacent chunks/pages). `Retriever.expand_neighbors(hits, window=1)` adds each hit's `chunk_id ± 1` *only within the same source* (chunk ids are sequential per document, but the last chunk of one PDF sits right next to the first chunk of the next, so a bare id check would leak across documents), tags added chunks via `hit.meta["neighbor_of"]`, and dedupes so no chunk id appears twice.
- **Neighbor expansion runs *after* the confidence gate, not before.** A confidence-gated miss shouldn't pay the extra context cost, and expansion is about giving the LLM fuller context for chunks already judged relevant — not about changing what gets judged. This also means `confidence` is always computed from the original (unexpanded) top hit, keeping it comparable with/without the flag for A/B evaluation.
- **`ask()` grew a new `expand_neighbors: bool = False` parameter** (default off, so every existing test and the frozen spec's behavior are unaffected). This is a deliberate deviation from the spec's fixed `ask()` signature, justified because the user requested this feature themselves, outside the original frozen spec, specifically so it could be A/B tested.
- **`Result.hits` reflects the *expanded* set when the flag is on**, not the original top-k, since that's what was actually sent to the LLM — this makes `src.eval.hit_at_5` honestly measure whether expansion increases the chance the gold page ends up in context, which is the whole point of testing it.
- **Verified against the real indexed corpus (not just synthetic fixtures)**: asking "What is Reciprocal Rank Fusion used for in retrieval?" with `force_route="hybrid"` returned `NOT_FOUND` (correctly normalized to "Not found in the documents.") without expansion, because the LLM only saw chunks not actually containing the definition — then a real, correct answer with expansion on, confirming the fix works on a genuine chunk-fragmentation case, not just in theory.
- **Full Step 8 eval was run on the real 26-paper corpus and 55 real questions; threshold sweep results were reported, not auto-applied.** `tune_thresholds()` showed the current `VECTOR_MIN_SIM=0.45`/`BM25_MIN_SCORE=5.0` give a 100% false-answer rate on out-of-scope questions in isolation (`force_route`-only configs; the router itself had 0% escalation and correctly routes greetings to `direct` before any of this applies). Inspecting the actual answers in `to_grade.csv` showed the deeper cause isn't purely a threshold problem: the corpus (papers about LLM evaluation/jailbreaks) contains example Q&A/adversarial-prompt text that BM25 matches lexically for unrelated casual queries, and the local 3B model sometimes completes that retrieved text instead of refusing. Per the spec, `config.py` was not edited automatically — the finding and sweep table are reported in the README for the user to act on.
- **Eval run latency figures are explicitly flagged as not a clean cross-config comparison.** The run shared a RAM-constrained machine with other applications during the session, and later configs (e.g. `router`, mean 54.8s) measurably slowed down mid-run independent of the strategy itself — documented in the README so the latency numbers aren't mistaken for a fair apples-to-apples speed comparison, while hit@5 (which doesn't depend on wall-clock speed) is unaffected.
- **Correctness grading was performed by a separate AI session against `expected_answer`, in `eval/to_grade.csv`, not invented by this session.** The graded output file (`to_grade_graded.csv`) wasn't saved into this repo, so the README's correctness table uses the aggregate scores and example answers as reported, not a row-level recount.
- **One flagged "wrong number" (ARES, Q24) was verified against the source PDF and found to be a false positive, not corrected elsewhere.** The grader marked an answer of "59.9" wrong against `expected_answer`'s "59.3," but the source paper itself states both figures (abstract vs. results section) for the same claim. The other two flagged numbers (HaluEval, HELM) were verified as genuine model errors. Since this affects at most 1 of 55 questions, the aggregate score table was not recomputed — the caveat is documented instead of silently fixed.
- **Neighbor expansion was measured with a one-off script (`run_neighbor_comparison.py`, in the scratchpad, not committed to the repo)** rather than adding a 7th config to `src.eval.CONFIGS`. It's a single real comparison (hybrid with/without the flag) answering one specific question, not a permanent part of the eval matrix; adding scratch tooling to the project for a one-time measurement would be scope creep beyond what was asked. Results (+0.04 hit@5 overall, concentrated entirely in `exact` questions: +0.06) are written into the README directly; raw answers are saved to `eval/to_grade_neighbors.csv` (gitignored, like the other generated eval CSVs) for optional correctness hand-grading later.
- **The deferred Step 5 ("5 queries side by side") and Step 6 ("baseline demo on 3 questions") demos used real questions picked from `eval/questions.json`**, not newly invented ones, since those are genuinely user-authored. Both ran via one-off scratchpad scripts (not committed), with results written directly into the README rather than keeping the scripts in the repo. The baseline demo's 2-of-3 broken citation markers (`[n]`, `[n3]` instead of a real number) are fresh, independent evidence of the same small-model instruction-following gap the full eval's correctness grading already surfaced at scale — found here with just 3 calls, before the router or confidence gating are even involved.
- **Added a corpus centroid gate (`Retriever.centroid_similarity`, `CENTROID_MIN_SIM`) to fix off-topic questions getting answered — the user's own diagnosis that the router's regex can't detect "is this topically about my documents" for a well-formed question (only for syntactically-greeting-shaped text) was correct.** A better embedding model would *not* have fixed this: the failure wasn't embedding quality, it was that the corpus genuinely contains near-identical text to the off-topic query (e.g. a benchmark paper's own "What is the capital of France? → Paris" example), so any embedding model correctly finds that chunk similar. The fix needed a *different* signal — comparing the query against the corpus's overall centroid, not any single chunk — not a better version of the same per-chunk signal.
- **The centroid is computed once per build (`compute_centroid`, reconstructed from the FAISS index via `index.reconstruct_n`, not re-embedded) and persisted to `data/index/centroid.npy`**, loaded eagerly (it's tiny) in `Retriever.__init__`. `centroid_similarity` raises `RuntimeError` rather than silently returning a meaningless number if an index built before this feature exists without a centroid file — the fix (`python -m src.indexer`) is one command, so a loud failure is better than a silent wrong gate.
- **`CENTROID_MIN_SIM=0.55` was set from real data, not guessed**: measured across all 55 real questions, general (out-of-scope) questions scored 0.44-0.59 on centroid similarity, scoped (real) questions scored 0.59-0.78 — a clean gap. 0.55 sits above the actual problem cases (0.44-0.51) and below every scoped question, without hugging the one borderline case ("Thanks, that was helpful!", 0.589 — already caught by the router's greeting regex before this gate is reached in normal operation, so its narrow margin doesn't matter in practice).
- **The gate is applied to all three retrieval-touching routes (`keyword`/`vector`/`hybrid`), not just `hybrid`**, since the originally-found "Paris" failure was specifically a BM25/keyword-route failure. It's checked alongside each route's own per-chunk confidence check (`VECTOR_MIN_SIM` for hybrid/vector; added fresh for keyword, which previously had no confidence gate at all besides the escalation trigger) — either failing returns "Not found" with no LLM call. `Result` gained a `centroid_sim` field (mirroring `confidence`) for logging/diagnostics, also added to `src.eval.run_config`'s per-question record.
- **Verified against the real corpus, re-testing the exact 4 documented failure cases**: all 4 now correctly return "Not found" across keyword, vector, and hybrid alike (previously `bm25` answered "Paris," `hybrid` wrote an actual poem and described real Mumbai weather). False-answer rate on general questions: 100% → ~17% (1 of 6 remaining, and that one is moot in real operation). A sanity check on 6 real scoped questions confirmed no regression (centroid 0.65-0.69, well above threshold, still answered normally). This measurement predates and isn't folded into the existing `eval/results.md`/correctness table — a full re-run would be needed to update those numbers, which wasn't done to avoid another multi-hour run; the README flags this explicitly.
- **Re-chunked with parent-child retrieval, not heading-based (structure-aware) chunking.** Heading chunking needs reliable heading detection, but `pypdf` on two-column arXiv PDFs yields flat text with no structural markers, so any heading regex would be guesswork. Parent-child needs no parsing: ~120-token *child* chunks (`CHILD_TOKENS`) are what gets embedded and BM25-indexed (precise matching), and each child's ~600-token *parent* (`CHUNK_TOKENS`) is what the LLM reads (no answer cut off at a small chunk's edge). `src.ingest` writes `parents.json` (1,564) and `chunks.json` = children (7,837, each with `parent_id`); `Retriever.to_parents` swaps retrieved children for their parents, collapsing siblings into one hit at the best child's rank/score. Parents never cross pages, so citations/hit@5 still point at one page. With no `parents.json` present every chunk is its own parent (old indexes and test fixtures keep working). Requires re-running `python -m src.ingest` then `python -m src.indexer`.
- **Fixed the rerank bug: the cross-encoder used to rerank only the TOP_K=5 hits hybrid search had already chosen**, so it could reorder them but never promote a better candidate from further down — which is why `hybrid+rerank` scored exactly the same hit@5 as `hybrid` (0.76). It now reranks a `RERANK_POOL_K=30` child pool, then collapses to parents and keeps `TOP_K`. Retrieval-only measurement (49 scoped questions, no LLM): hit@5 0.76 → 0.90, MRR 0.63 → 0.68, `exact` 0.69 → 0.88. Chunking alone lifted every method (vector 0.63 → 0.76, hybrid 0.76 → 0.80, bm25 0.78 → 0.84).
- **Rerank scores are used as-is (0-1 probabilities).** I first wrongly assumed `CrossEncoder.predict` returned raw logits and added a sigmoid; with sentence-transformers 6.2.0 it already applies one for single-label models, so mine double-applied it and squashed every score into 0.5-0.73 (caught because scoped questions' top scores all clustered at 0.731 = sigmoid(1.0)). Ranking was never affected (monotonic), only confidence values. Removed. The rerank path is gated on its own `RERANK_MIN_PROB` rather than the cosine `VECTOR_MIN_SIM`, since the scales differ.
- **Neighbor expansion stays off (`expand_neighbors=False`, the default) with parent-child chunking.** Parents already carry the surrounding context neighbor expansion existed to supply. Measured: it adds only +0.02 hit@5 on hybrid+rerank (1 of 49 questions) and +0.06 on plain hybrid, but sends a mean of 11.6 parents (~7,000 tokens) instead of 5 to a 3B model, and its hit@5 is flattered because neighbors count as "retrieved". The code is kept (and tested) for indexes built without parents; do not combine it with parent-child by default.
- **Re-calibrated the confidence thresholds on the new index (retrieval-only, all 55 questions; in-sample, so margins were kept).** The old values were the spec's placeholders and the chunk sizes they were measured on no longer exist. `BM25_MIN_SCORE` 5.0 → 15.0 (scoped min 17.7, so 5.0 never fired; at 15 only weak keyword matches escalate to hybrid, which has the stronger gates). `VECTOR_MIN_SIM` 0.45 → 0.60 (scoped min 0.665; 0.60 answers all scoped questions and halves the off-topic pass rate). `RERANK_MIN_PROB` = 0.5 (scoped min 0.84; off-topic scored 0.01/0.04/0.47 or ≥0.95, and the ≥0.95 ones are stopped by the centroid gate, so the combined gate is what matters). Centroid gate re-checked after the centroid was recomputed over children: general 0.46-0.61, scoped 0.60-0.77, so `CENTROID_MIN_SIM=0.55` still separates them.
- **Not done / still open:** the LLM-based eval (`python -m src.eval`) and hand-graded correctness have *not* been re-run on the new index, so the README's correctness table (42-53%) describes the old chunking; and the threshold tuning shares data with the eval set (no held-out split yet).
- **Wrote a held-out question set (`eval/heldout_questions.json`, 39 questions) because the 55 eval questions had been used to tune every threshold.** 17 exact, 10 conceptual, 12 off-topic (two deliberately LLM-adjacent: "best LLM today", "GPT-5's MMLU score"). Each in-scope question's `gold_pages` is computed by regex-matching evidence text against page text of the gold PDF (a validator script refuses to write the file if any evidence is missing), never typed by hand; the facts chosen were not used in the original 55. Written by the assistant, not the user, so it may be easier than third-party questions. `src.eval` gained `--questions` (non-default files write `results_<name>.md`/`to_grade_<name>.csv` and skip `tune_thresholds`, so a held-out set is never tuned on) and `--configs` (partial re-runs get a suffix and never overwrite a full run).
- **Correctness was graded by an AI session, not a human, with explicit rules:** exact questions by whether the key fact is stated (regex per question, long raw dumps checked by eye and counted wrong unless they quote a passage that plainly states the answer); conceptual questions read against `expected_answer`; off-topic questions correct if refused (or a normal reply on the `direct` route). Held-out result: in-scope 44-59% across configs, hybrid+rerank/router best (16/27) with 12/12 and 11/12 off-topic handled. On the original 55 (in-sample): hybrid+rerank/router 43/55 = 78%. The old 42-53% was a different grader with stricter format rules, so the size of the improvement is not like-for-like; the 55-question numbers are optimistic (in-sample), the held-out ones are the estimate to trust.
- **Run-to-run noise is as large as most config differences.** The identical hybrid+rerank config scored 16/27 in one held-out run and 20/27 in the next (only a token cap and temperature 0 changed, plus sampling nondeterminism before that). Correctness differences of 3-4 answers at n=27 are not conclusions; retrieval hit@5 (stable) ranks configs more reliably than correctness does.
- **Fixed three things the held-out eval exposed.** (1) A router answer ran to ~209,000 characters because `src/llm.py` set no output limit; now `LLM_MAX_TOKENS=512` and `LLM_TEMPERATURE=0.0` are passed to Ollama (router mean latency 63 s -> 21 s). (2) The app's rerank checkbox and the eval `router` config defaulted to no reranking, which refused 8 of 12 off-topic questions versus 12 of 12 with it; both now default to rerank (`ask()`'s own default stays `False` so library callers and tests don't load the 1GB reranker). (3) `[1] [2] [3] NOT_FOUND` was not treated as a refusal; `is_not_found` now ignores citation markers and punctuation.
- **Answer-prompt A/B on hybrid+rerank, held-out set:** v1 (original) 31/39, v2 (reworded prompt + retry) 32/39, v1r (original prompt + retry) 33/39. v2 fixed bare-citation answers (2 -> 0) and gained two in-scope answers but loosened refusals (it answered "translate good morning" from corpus text and a linked-list question from the model's own knowledge). The retry only fires when a reply has no words, which is never a correct answer, so it can't reduce in-scope accuracy; combined with the original prompt's refusal behavior that is `PROMPT_VERSION="v1r"`, now the default (override with the env var). The v1r margin is within noise; it was chosen as the safest by construction. A retry can turn a bare off-topic reply into fabricated content (seen once, the linked-list question).
- **Still open:** the dominant error is the 3B generator, not retrieval (hit@5 0.93 vs ~59% correct on held-out) — wrong-paper answers (MMLU-Pro when asked about MMLU), context pasted instead of answered, and exact-fact misses where the right page was retrieved. Next steps with real expected value: a larger/better-instructed model (e.g. a 7-8B), constrained JSON citations, query decomposition for two-part questions, and an NLI/LLM grounding check. Also: no confidence intervals or paired tests yet, and the held-out set is small.
- **Tried to make the 3B model do better without a bigger model; results were mostly speed and format, not accuracy.** Built four switchable techniques and compared them with a generation-only harness on cached retrieval (identical context per variant; developed on the original 55 questions, confirmed on the held-out set; the harness is a scratch script, not in the repo): (1) structured JSON output via Ollama's `format` schema (`PROMPT_VERSION=v3`), (2) sentence-level context selection with the cross-encoder (`CONTEXT_MODE=sentences`), (3) a number-grounding check with one retry (`GROUNDING_CHECK`), (4) an adaptive mode choosing (2) only for single-fact questions (`CONTEXT_MODE=auto`). Dev (49 in-scope): old prompt/full context 38 correct, v3/full 39, v3/sentences 37; held-out in-scope: old 22, v3/full 19, sentences 19-20.
- **Structured output (v3) is cleaner but not more accurate, so it stays opt-in.** Literal "[n]" citations 7 → 0, parsed citations 36 → 42/49, and 12/12 off-topic refusals on held-out, but `found:false` produced 3-4 false refusals on in-scope questions (e.g. HELM, Vicuna bench) and the held-out in-scope score fell (19 vs 22). Default stays `v1r`.
- **Sentence-level context is ~4.5× faster (5 s vs 17-21 s per answer, 800 vs 3,300 prompt tokens) and as good or better on single-fact lookups, but worse on conceptual questions** (held-out 6/10 vs 8/10; once it fabricated an unrelated answer about clinical guidelines for the LLM-as-a-Judge survey question). Hence `auto`: `router.is_factoid_question` (regex on the question start, vetoed by explanatory words like why/explain/differ/how does) sends lookups to sentences and everything else to full parents. It errs on the safe side: on the 76 labelled in-scope questions it sent 0/27 conceptual and 40/49 exact questions to the fast path (88% agreement overall); a false negative just means full context. The regexes were written after seeing the dev questions, so the 88% is somewhat optimistic. `auto` is the default; its end-to-end score is composed from the measured per-mode outputs (exact 25/32 dev, 14/17 held-out; conceptual unchanged; dev mean answer latency 16.5 → 11.5 s), not from a separate full run.
- **The number-grounding check never changed an answer.** The model rarely states numbers absent from the retrieved text; its wrong-number errors (e.g. "30K votes" instead of "240K") use a number that really is in the context, which a presence check can't catch. Kept as an off-by-default option (`GROUNDING_CHECK=1`) and noted as not useful here.
- **Lesson on workflow:** two scratch-script bugs (a Windows default-encoding crash while saving a "≥" character, and shell/tool escaping silently turning `\b` into a backspace in a regex) were caught only because I checked intermediate results; the second made a regex fail silently until a unit test failed. The classifier regexes now have tests.
- **Embedding model: e5-base-v2 over bge-small; bge-large and Qwen3-Embedding-0.6B skipped.** On the Docling-Markdown chunks e5-base lifted hybrid hit@5 to 0.857 dev / 0.889 held-out (bge-small 0.837 / 0.815). The two larger models would take hours on CPU-only torch for an unmeasured gain. bge-base is the only other candidate worth running. Not final until the index is rebuilt and `VECTOR_MIN_SIM` / `CENTROID_MIN_SIM` are re-derived.
- **PDFs are converted to Markdown with Docling before chunking; formula decoding is GPU-only.** Docling reads the text layer (OCR only for image regions), keeps tables as pipe tables and saves figures; its formula model took ~195 s per formula on CPU, so formulas are skipped there and missing from the Markdown.
